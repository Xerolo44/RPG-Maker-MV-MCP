# RPG Maker MV MCP v0.5 — Overview, Scope and Release Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement the track plans task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This file is the **spec** the three track plans argue from; read it first.

**Goal:** Ship 0.5.0 so a small game can be built from start to finish and checked for dead ends: import and catalogue assets, write cutscenes without hand-built command lists, and analyse a project's switches, variables and progression.

**Architecture:** Three independent tracks built one after the other on one integration branch `release/0.5.0` (base: `main` at 0.4.0 + CI fix), then one release task and ONE pull request. Same conventions as 0.4: pure logic in `src/*.ts` (unit-tested against compiled `dist/`), thin zod-validated tool registration in `src/tools/*Tools.ts`, one end-to-end smoke assertion per tool in `scripts/smoke.mjs`.

**Tech Stack:** TypeScript (strict, NodeNext ESM), `@modelcontextprotocol/sdk`, zod, `node:test`. No new dependencies.

## Track plans

| Track | File | Delivers |

| E | `2026-10-25-v0.5-e-assets.md` | `import_asset`, `list_assets`, `preview_asset`, new profile group `assets`, `Project.writeBinary` |

Order: E → F → G → release task R. Tracks do not depend on each other except that G's reference extractor must also understand the commands F makes easy to write (listed in G1).

## Explicitly NOT in 0.5

Playtest runner (`playtest_scenario`, needs a real MV engine to verify), dungeon/village/overworld generator additions, battle/enemy helpers, deployment/export, plugin help parsing, MZ support, asset deletion, image conversion/resizing on import, audio transcoding. Do not add them to a 0.5 task.

## Global Constraints

- Node `>=18`; CI matrix is Node 18.x and 20.x on ubuntu-latest and windows-latest and runs `npm run test`. Nothing may need a browser, an RPG Maker install, a network, or a glob argument to `node --test`.
- `"type": "module"`; TypeScript `strict`, `module`/`moduleResolution` `NodeNext`; relative imports end in `.js`.
- Tool shape: `server.registerTool(name, { title, description, inputSchema: { ...zod } }, safe(async (args) => textResult(...)))` from `src/util.ts`; descriptions are written for an AI reader; every new tool calls `project.root` first so it answers `No project selected…` before set_project.
- All project writes go through `Project` (`writeJson`/`writeText`, and `writeBinary` from Track E) so backups and changesets keep working. No new raw `fs` writes in `src/tools/`.
- MV arrays are 1-indexed with `null` at 0; map `events` too (`[]` and missing `events` must be tolerated and normalised to `[null]` when writing).
- Event command lists end with `{code: 0, indent: 0, parameters: []}`; every generated list passes `validateCommandList(terminated(list))`.
- Command parameter layouts in these plans come from knowledge of the MV engine; implementers verify against `src/reference.ts` and record discrepancies; where the reference is silent, the layout in the plan is used and listed in the report as "unverified against engine source". Corrections go into `src/reference.ts`.
- Version bump at release: `package.json`, `package-lock.json` (top-level `version` and `packages[""].version`), `src/index.ts` (`McpServer` version), `server.json` (top-level `version` and `packages[0].version`) → `0.5.0`. `CHANGELOG.md` needs a `## [0.5.0]` section (the release pipeline extracts the release notes from it and fails without it).
- Merging the PR to `main` triggers the release pipeline (npm, MCP Registry, GitHub Release). Do not merge; do not push tags.
- Commit trailer: `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. Never commit to `main`.

## Review Focus

1. **No project selected:** every new tool returns the standard error. [E2, E3, G2, G3]
2. **Hostile names and paths:** asset names/folders, source paths, usage ids: reserved Windows names, `..`, separators, NUL, unicode lookalikes, trailing dot/space, absurd lengths — rejected before any file access. [E1, E2]
3. **Large inputs:** a 5 000-event project indexes in under 2 s; `analyze_progression` terminates (bounded fixpoint) on cyclic maps/events; list/usage outputs are capped with a `truncated` count. [G1, G3, E3]
4. **Malformed project data:** `events: [null]`, pages without `list`, commands with missing parameters, huge ids, unreadable map files — skipped or reported, never thrown out of a handler. [G1, G2, G3, F1]
5. **Changesets:** a binary import refuses (clearly) inside an open changeset; all other new tools see staged data (read through `Project`). [E2, G1]
