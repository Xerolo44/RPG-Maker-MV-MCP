# v0.5 Track G — Usage Index and Progression Analysis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Answer "where is this switch/variable/item/map/… used?" (`find_usages`) and "can the player get from the start to X, and what can never happen?" (`analyze_progression`).

**Architecture:** One shared, pure index (`src/eventIndex.ts`) turns a project into event pages plus typed references (reads / writes / uses) extracted from page conditions, event commands, selected database fields and System.json. `find_usages` queries it; `analyze_progression` runs a bounded monotone fixpoint over it (an over-approximation: everything that could ever become true under "any triggerable page may run, guards ignored").

**Tech Stack:** TypeScript, zod, `node:test`. No new dependencies.

**Spec:** `docs/superpowers/plans/2026-10-25-v0.5-00-overview.md`.

## Global Constraints

- Node `>=18` ubuntu + windows; ESM, strict, NodeNext, `.js` suffixes; both tools register inside the existing `registerAnalysisTools` (group `analysis`); data is read with `project.readJson` (staged changeset content is visible).
- Reference kinds (exact): `switch variable item weapon armor skill state actor class enemy troop commonEvent map`. Roles: `read`, `write`, `use`.
- Not understood and therefore reported as uncertainty, never guessed: script commands (355/655), plugin commands (356), variable-designated transfers (201 with first parameter 1), variable-designated battles (301 with first parameter 1 or 2), notetags and plugin parameters.
- Caps: ranges in 121/122 expand to at most 1000 ids per command; tool outputs list at most 100 locations per role (`limit` ≤ 500) with a `truncated` count.
- Branch: stay on `release/0.5.0`. Test fixtures: a small helper `test/helpers/fixtureProject.mjs` (not matched by the runner, which only runs `test/*.test.mjs`) creates a temp MV-shaped project from plain objects; create it in Task 1 and reuse it.

### Task 3 (G3): Progression analysis core

**Files:**
- Create: `src/progression.ts`, `test/progression.test.mjs`

**Interfaces:**
- Consumes: G1 (`ProjectIndex`, `EventPage`, `commandRefs`, `hiddenKind`).
- Produces:
  - `export type Goal = { switch: number } | { mapId: number } | { event: { mapId: number; eventId: number } }`.
  - `export interface ProgressionReport { startMapId: number; reachableMaps: number[]; unreachableMaps: number[]; deadEndMaps: number[]; deadPages: { kind: "map"|"commonEvent"|"troop"; mapId?: number; eventId: number; page: number; reason: string }[]; switches: { neverSet: number[]; neverRead: number[] }; variables: { neverSet: number[]; neverRead: number[] }; goal?: { target: string; reachable: boolean; blockedBy: string[] }; uncertainty: { scriptCommands: number; pluginCommands: number; variableTransfers: number; variableBattles: number; confidence: "high"|"low" }; edges: { from: number; to: number }[]; notes: string[]; truncated: boolean }`.
  - `export function analyzeProgression(index: ProjectIndex, opts: { goal?: Goal; limit: number }): ProgressionReport`.
- Algorithm (fixed; implement exactly): state = reachable maps `R = {startMapId}`, ON switches `S = ∅`, written variables `W = ∅`, gainable items/weapons/armors `G` (kind+id), party actors `A` = `index.partyMembers`, self switches ON `F` (mapId,eventId,ch), called common events `C`, used troops `T`. Loop until no set grows (each set only grows, so it terminates; also cap at 10 000 iterations and set `truncated`): a page is *triggerable* if (map page) its map ∈ R, or (commonEvent page) its id ∈ C or its derived switch condition holds, or (troop page) its troop ∈ T — AND all its conditions are *satisfiable*: switch1/2 ∈ S; variable: `W` contains it or `0 >= variableValue`; item ∈ `G`; actor ∈ `A`; self switch: `F` contains (mapId,eventId,ch) — where a page's *own* self-switch setting counts for other pages of the same event. For every triggerable page, apply ALL its commands ignoring guards: `121` ON → `S`; `122` → `W`; `123` ON → `F` (this event); `201` direct → `R` (+ an edge); `126/127/128` with operation 0 → `G`; `302/605` goods → `G`; `129` add (p[1]=0) → `A`; `117` → `C`; `301` direct → `T`; enemy drops are always gainable (add all drop refs to `G` once at start); a reachable map's `encounterList` troops → `T`. Dead page = page on a reachable map (or any common event/troop page) that is never triggerable at the fixpoint; `reason` names the first unsatisfied condition (`"switch 12 is never switched ON by any reachable event"`, `"item 5 can never be obtained"`, …). `deadEndMaps` = maps in `R` with no direct `201` on any of their pages. `switches.neverSet`/`neverRead` and variables likewise come from the full ref list (all pages, reachable or not): read with no write / written with no read. `confidence` is `"low"` when any hidden count is > 0 (in triggerable pages), else `"high"`. Goal: switch → `S` contains it; map → `R` contains it; event → some page of that event is triggerable; when not reachable, `blockedBy` lists up to 10 strings: for a switch the pages that set it with their first unsatisfied condition (or "no event ever sets switch N"), for a map the transfer pages into it with their unmet conditions (or "no event transfers to map N"). All lists are sorted numerically and capped at `limit` (set `truncated`).
- [ ] **Step 1: Write failing tests** (fixture project through `buildProjectIndex`): start map with a door to map 2 gated by switch 5, which an NPC on the start map sets → map 2 reachable; same project without the NPC → map 2 unreachable, `goal {mapId: 2}` unreachable with `blockedBy` mentioning switch 5; a chain of three switches across three maps; an item gate satisfied by a chest (126) and by a shop (302) and by nothing; a variable gate `>= 3` satisfied only when some page writes the variable; self-switch chest (page 2 needs self switch A set by page 1); a common event that sets a switch, called only from an unreachable map → switch not set; a parallel common event gated by a switch; troop pages; enemy drops make an item gainable; cyclic maps (A↔B) terminate; a dead-end map; `neverSet`/`neverRead`; `confidence` low with a script/plugin/variable-transfer in a triggerable page and high when the same commands sit only on an unreachable map; goal switch/event; limit and `truncated`; idempotent (calling twice gives equal reports); a 200-map chain finishes in under 2 s.
- [ ] **Step 2: Run, expect FAIL.** **Step 3: Implement.** **Step 4: PASS; `npm test`.**
